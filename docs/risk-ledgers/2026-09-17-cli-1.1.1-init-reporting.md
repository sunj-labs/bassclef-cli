# Pre-mortem light — cli 1.1.1 init reporting

Assume it is 2026-09-24. Cli 1.1.1 shipped and it went badly. What went
wrong?

## Lens 1 — Linus Torvalds (do not break the people using this)

| ID | Risk | Fold |
|---|---|---|
| L1 | Sync reads a 379-entry manifest and its output explodes from one line to hundreds. Adopters think sync broke. | Verify `classify()` returns no-op for unknown template names. Confirm the grouped directory output at sync.ts L389-437 handles the volume. Add a test. |
| L2 | Sync tries to manage walker files and overwrites adopter edits. | Mark every walker entry with a template name that is not in the TEMPLATES table. Test that sync takes no action on them. |
| L3 | An adopter script reads `--json` from stderr today. Moving it to stdout breaks that script. | Real but accepted per ADR-031 at this adopter count. Name it in the changelog. Keep the JSON identical in content on both streams for one release? No — dual-emit invites a worse ambiguity. Ship the move and say so. |
| L4 | A 1.1.0 manifest on disk meets 1.1.1 code. The shape version differs. Init or sync refuses. | Read `readManifestShapeVersion` before changing the gate. Accept shape 2 and shape 3 on read. Only write shape 3. |
| L5 | `generated_by` still reads `@thebassclef/core`, a deprecated package. Adopters chase a dead name. | Fix it in this goal. Read the package name instead of hardcoding it. |
| L6 | The manifest grows by roughly 380 entries. On a large tier it could reach megabytes. | Measure the written size in a test. If it is over 1 MB, reconsider what each entry stores. |

## Lens 2 — Tony Hoare (say what must be true before and after)

| ID | Risk | Fold |
|---|---|---|
| H1 | "Authoritative" is never defined, so nobody can test it. | Write the postcondition as a number: manifest entry count equals config writes plus `copiedEntries.length`. Assert it. |
| H2 | Refused and errored files are absent from the manifest, so a partial init looks complete. | Record refused and errored entries too, with their outcome. The manifest describes the run, not just its wins. |
| H3 | Dry run writes a manifest that claims files landed. | Assert the dry-run path writes no manifest. Test it. |
| H4 | The JSON report and the manifest disagree about counts because each counts separately. | One classifier function feeds both. Assert the two agree in a test. |
| H5 | Hashing 378 files slows init noticeably. | Decide per entry type. Hash what sync may manage. For verbatim walker copies, record the path and skip the hash. State the reason in the ADR. |

## Lens 3 — John Ousterhout (one deep module, not three shallow ones)

| ID | Risk | Fold |
|---|---|---|
| O1 | Category classification gets copy-pasted a third time, so banner, JSON, and manifest drift apart. | Extract one `classifyCatalogEntry` function. All three callers read it. |
| O2 | `init.ts` is already long. Three more features make it unreadable. | Move the reporting concern into its own module with a narrow interface: entries in, report out. |
| O3 | The root-doc heuristic (repo-root file starting with a capital letter) is guesswork that will misfire. | Keep it, but put it behind the single classifier so one fix corrects every caller. Add a test naming the files it must catch. |
| O4 | The `--json` change scatters `if (json)` checks through the print path. | Choose the output stream once. Pass a writer. Do not branch at every call site. |
| O5 | Tests assert on exact printed strings and break on every wording change. | Assert on parsed JSON and on manifest structure. Keep string assertions to the few lines that are the contract. |

## Folds taken into the plan

L1, L2, L4, L5 → Step 3 acceptance and tests.
L3 → changelog wording, Step 7.
H1, H2, H3, H4 → Step 3 postconditions written as assertions.
H5 → ADR-010 decision on hashing.
O1, O2, O4 → Step 3 ships the shared classifier and the reporting module first.
O3, O5 → test discipline across Steps 3-5.
L6 → measured in Step 3, reported at Step 6.
