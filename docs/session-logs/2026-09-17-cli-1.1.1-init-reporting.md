# Session log — 2026-09-17 — cli 1.1.1 init reporting

## What shipped

PR #98, open and mergeable. Three commits, 32 files, 2,146 insertions.

`bassclef init` wrote 499 files and reported something else. Three
defects, all in one output path, all found in the 1.1.0 cold-adopter
smoke:

- The install record named one file (#93), so `bassclef sync` only ever
  checked that one.
- `--json` went to standard error while 151 human lines followed it on
  standard output (#94), so `tail -1` returned prose.
- The report counted hooks and none of the other eleven families (#95).

All three are fixed and verified against the built cli, not just the
test suite.

## What the design turned out to be

The three tickets read as three patches. They were one cause:
`init.ts` computed a full picture of the run, used a slice of it for the
terminal banner, and discarded the rest. The record and the JSON each
re-derived a different, smaller slice.

Two new modules close that: one classifier sorts a path into a family,
and one report object is built once and read by all three writers.

The reframe that mattered came from reading the existing artifacts rather
than the tickets. `ADR-002` §Amendment 2026-09-13 already decided the
record's "file-count grows to match the extended tree," and `UC-init.md`
L75 already stated "each file has a SHA-256 content hash recorded." #93
was a regression against a written contract, not a feature request. That
changed the ADR from a decision into a repair, and it changed the use
case amendment from adding a promise to making an existing one countable.

## Both review councils earned their place, and they caught different things

**RFC-0004, on the design, before any test existed.** Five lenses outside
the authoring set, fourteen findings, three HIGH. The one that mattered:
the walker writes undeclared hook helpers to both user and project scope,
so two entries share one bundle-relative path, and `sync.ts:446` looks
entries up by path alone. Recording every file — the whole point of #93 —
would have turned a dormant collision into a live one. Keying the record
on path and scope together came out of that review, before a single test
was written. Finding it after the tests would have meant rewriting them.

**RFC-0005, on the shipped code.** Three more findings, two of them
defects in code written earlier in the same session:

- `totals.files` counted successes while the record also held refused
  entries, so on any re-run the two disagreed by exactly the refused
  count — measured at 434 against 499 with 65 refusals. The goal set out
  to close a class where two counters disagree, and the first
  implementation put that class back in a new place.
- `hooks.declared` counted settings.json commands while `hooks.copied`
  counted hook files including helpers. A reader subtracting them saw 61
  unexpected hooks. That is ticket #95's complaint — mixed units under one
  heading — reintroduced two fields over.

Running only one of the two councils would have shipped a defect either
way. That is the note worth carrying forward.

## What I got wrong

**My own test passed for the wrong reason.** The assertion that the
record's entry count equals `totals.files` ran on a fresh init, where
refused is zero. It could not tell a correct report from one counting
only successes. The fix adds a second init into a populated home so the
refusal case is exercised. Worth remembering: an assertion that can only
be reached with a zero on both sides is not an assertion.

**`git add -A` swept 575 synced files into the branch.** Bassclef syncs
several hundred files into `.claude/`, nothing gitignores them, and they
sit untracked. A blanket add produced a branch of 648 files and 124,440
insertions for a 32-file change. I caught it at closeout while gathering
the diffstat for this log — which is late. Recovery was a soft reset, a
re-stage by path, three fresh commits, and a force-push onto a PR nobody
had reviewed yet.

Filed as #99, because it is not a mistake specific to me: any adopter
repo carries the same trap, and cli 1.1.0 made it about five times bigger
by growing the synced set.

**One unexplained test failure.** One run of the suite reported 1 failure
out of 345. Ten subsequent runs, including five of the suspected file in
isolation, were clean, and I never identified which test it was. Recorded
here rather than called resolved, because five clean runs do not prove a
race is gone.

## Measured rather than assumed

- Install record: 198 KB, 499 entries. The ADR first estimated ~100 KB.
  The measured figure is nearly double, which is why the test asserts a
  1 MB ceiling instead of trusting the estimate. The ADR now carries the
  correction.
- Hashing 498 files: 114-122 ms across three runs, taken from bytes
  already in memory.
- Adopter count: 244 downloads in the 30 days to 2026-09-11, first
  published 2026-09-02. An earlier draft of the ADR asserted the count
  was low without measuring it. Downloads count machines, so the real
  number is unknown — but it is not demonstrably zero, which is why the
  `failed` field survives a release rather than being cut today.
