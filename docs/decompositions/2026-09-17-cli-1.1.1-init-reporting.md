# Decomposition — cli 1.1.1 init reporting

## What changes and why the shape is what it is

Three tickets. One cause. `init.ts` computes a full picture of what it
wrote, uses a slice of that picture for the terminal, and throws the rest
away. The manifest and the JSON report each then re-derive a different,
smaller slice.

The fix is not three patches. It is one description of the run, computed
once, read by three writers.

## Responsibilities today

| Responsibility | Where it lives now | Problem |
|---|---|---|
| Copy a file and remember it | `copy-substrate.ts` `copyOne` | Remembers path and scope; forgets the hash it could take for free |
| Sort a path into a family | `init.ts` L330-370, inline | One copy, thrown away after the banner prints |
| Count hooks | `init.ts` L296-310, inline | Second classification pass over the same list |
| Print for people | `init.ts` L270-400 | Writes to stdout unconditionally |
| Print for machines | `init.ts` L409-419 | Writes to stderr, carries hook fields only |
| Record for tools | `init.ts` `writeManifest` L612-645 | Sees only the config-composer results |

Four separate walks over one list, three disagreeing outputs.

## Responsibilities after

| Responsibility | Assigned to | GRASP reason |
|---|---|---|
| Know what was written, including the hash | `CopiedEntry` in `copy-substrate.ts` | Information Expert — `copyOne` holds the bytes at the moment of the write |
| Sort a path into a family | `classifyEntry` in new `src/lib/catalog-classify.ts` | Pure function, one rule, no callers duplicating it |
| Build the run description | `buildInitReport` in new `src/lib/init-report.ts` | Creator — it owns the one object all three writers read |
| Print for people | `renderHumanReport` | Takes a writer, so the stream is a parameter not a branch |
| Print for machines | `renderJsonReport` | Serializes the same object; no second count |
| Record for tools | `writeManifest` | Reads the same object; no third count |

## Module shape

```
copy-substrate.ts
  copyOne ──▶ CopiedEntry { path, scope, content_hash_sha256, outcome }
                     │
                     ▼
catalog-classify.ts
  classifyEntry(path) ──▶ Family        (pure; one rule; ADR-057 prefixes)
                     │
                     ▼
init-report.ts
  buildInitReport(entries, configResults, tier) ──▶ InitReport
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
  renderHuman   renderJson    writeManifest
   (stream)      (stdout)      (.bassclef/)
```

`InitReport` is the narrow interface. Everything above it counts. Nothing
below it counts.

## Pattern calls

- `@pattern patterns/code/gof/strategy.md` — the output writer is chosen
  once from the `--json` flag and passed down, rather than each print
  site asking whether JSON is on. This is what closes risk O4.
- `@pattern patterns/code/fowler/value-object.md` — `InitReport` is
  built once and read three times. It has no behavior and no identity.

Both annotations go in the source they describe, per
`.claude/rules/pattern-annotation.md`. Annotations are only written after
confirming the catalog entry exists; if it does not, the annotation is
dropped rather than invented.

## Contracts (Hoare)

`classifyEntry(path)`

- Precondition: path is adopter-relative, not absolute
- Postcondition: returns exactly one family; never throws; unknown paths
  return `other` rather than being silently dropped

`buildInitReport(entries, configResults, tier)`

- Precondition: entries came from one completed copy run
- Postcondition: `report.totals.files` equals `configResults.length +
  entries.length`. The per-family counts sum to `entries.length`. The
  same object feeds all three writers, so the three cannot disagree.

`writeManifest(targetDir, report)`

- Precondition: not a dry run
- Postcondition: `manifest.files.length === report.totals.files`. Every
  entry carries a `source` and an `outcome`. Bundle entries carry a
  template name absent from the sync TEMPLATES table.

`renderJsonReport(report, stdout)`

- Precondition: `--json` was passed
- Postcondition: stdout received one JSON object and no other bytes

## What must not change

`bassclef init` with no flag prints the same lines in the same order to
the same stream. This is the Linus constraint and it is the first thing
the tests pin.

`bassclef sync` takes no new action. Bundle entries reach
`sync.ts:139-148`, which returns a no-op for an unknown template. A test
asserts the action count is unchanged against a 379-entry manifest.

## Test order (Beck)

1. Characterize the current non-JSON output before touching it. That test
   must stay green through every later step.
2. Characterize current sync behavior on a 1-entry manifest.
3. Then `classifyEntry`, alone, against the eleven families plus `other`.
4. Then `buildInitReport` totals, against the postconditions above.
5. Then the manifest count postcondition.
6. Then sync against a 379-entry manifest: same actions as step 2.
7. Then the stdout-only JSON assertion.
8. Then the JSON shape.

Steps 1 and 2 are the safety net. They are written first and they are
never edited afterward, per Feathers.

## Open question carried into the review

Sync prints a grouped directory summary for a large manifest
(`sync.ts:389-437`). Nobody has run it against 379 entries. The test at
step 6 measures the output, and the review reads the result before the
release step.
